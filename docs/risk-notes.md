# Risk Notes — will-style

Every area below has **zero automated test coverage** and **zero CI** — that's the baseline for the whole gem, not called out per-row. What varies is business criticality, coupling, and how well-understood each area is.

## SCSS / design tokens (`lib/assets/stylesheets/will_style/`)

- **Business criticality**: High — this is the gem's core deliverable; every consuming app's visual identity depends on it.
- **Test coverage**: None (no visual regression testing, no snapshot tests).
- **Coupling**: Moderate. 58 partials organized by convention (core/mixins/elements/components) with two entry points (`will_style.scss` for app styles, `email.scss` for inline email styles). Bootstrap 5.3 variable overrides mean upgrades to the `bootstrap` npm/gem pair could silently change resolved values here.
- **Understood?**: Mostly yes — conventional SCSS organization, self-documenting file names. The one soft spot: 22 uses of the legacy `@import` directive vs. 1 `@use`, which is a known-deprecated pattern in Dart Sass but not yet causing failures.

## Icon font system (`will-icons/` + `lib/assets/fonts/will-icons/`)

- **Business criticality**: Low-to-moderate — small, brand-specific glyph set (play/pause/arrows/logo), not the primary UI icon system (Font Awesome covers that).
- **Test coverage**: None.
- **Coupling**: Low technically (just CSS `@font-face` + PUA codepoint mapping), but **high process coupling to a tool outside this repo**: the compiled font files are generated by Fontastic (fontastic.me), an external, manual, undocumented step. There is no build config, no source-to-output pipeline, and no regeneration instructions committed anywhere.
- **Understood?**: **Least understood area in the repo.** If a new glyph is ever needed, or the existing font needs to be rebuilt (e.g., to add `.woff2`, which is currently missing), it's unclear whether anyone still has Fontastic access or knows the exact regeneration steps. This is the single biggest "bus factor" risk found in the survey. See [open-questions.md](open-questions.md).

## JavaScript behaviors (`app/javascript/will_style/`)

- **Business criticality**: Moderate — UI behaviors (dropdowns, modals, form validation, image loading, animated elements) are visible and functional, but failures tend to be locally contained (one broken widget) rather than app-wide.
- **Test coverage**: None (no Jest/Mocha, no test harness of any kind for JS).
- **Coupling**: High internally — all 18 files are IIFEs sharing a single global `window.WillStyle` namespace with an implicit load-order dependency (no ES module `import`/`export`), keyed off `turbo:load` for re-initialization on Turbo page changes.
- **Understood?**: Reasonably well-documented by file/directory naming, but `components/dropdowns.js` is a **hand-rolled reimplementation of Bootstrap's dropdown behavior** rather than a call into Bootstrap's own JS API — a divergence from the library's intended usage that a future maintainer could easily "fix" by accidentally reverting to real Bootstrap dropdowns and breaking the hover behavior this file exists to add. Worth a comment/doc note before anyone touches it.

## Dual JS loading system (Sprockets manifest vs. importmap)

- **Business criticality**: Moderate — both `app/javascript/will_style.js` (Sprockets `//= require`) and `config/importmap.rb` (`pin_all_from`) currently target the same files; if a consuming app is on one asset pipeline strategy and this drifts, JS could silently fail to load or double-load.
- **Test coverage**: None.
- **Coupling**: High — this is a cross-cutting concern touching every consuming app's asset pipeline configuration, not just this gem's internals.
- **Understood?**: Not fully — it's unclear from the code alone whether this is an intentional dual-support design (some consumers still on Sprockets-only, others on importmap) or an incomplete migration that should be finished by removing one path. This materially affects modernization sequencing (see [open-questions.md](open-questions.md)) and should be resolved early, since JS loading strategy is foundational to several downstream cleanup items (ESM conversion, removing the Sprockets manifest, etc.).

**Resolved 2026-08-11 (item C1)**: confirmed incomplete migration, not intentional dual-support. `app/javascript/will_style.js` is no longer a Sprockets manifest — rewritten as a plain ESM entry point (same file, same pinned name, same load order, contents now `import` statements instead of `//= require`). `config/importmap.rb` is the only loading path now. The still-open risk this leaves behind: the file-count/business-criticality assessment here was about the *dual-path* risk specifically, which is closed; the underlying coupling (21 order-dependent IIFEs sharing a global namespace) remains until item C2 converts them to real modules — see [specs/15](specs/15-remove-sprockets-js-manifest.md)'s Outcome for what's verified vs. what still needs a live consuming-app smoke test.

**Also resolved 2026-08-11 (item C2, same day)**: the underlying coupling is gone too — all 20 behavior files are real ES modules now, IIFE wrappers removed. Global-namespace reliance is down to three deliberate compatibility shims (`Settings`, `Events`, `Forms.initializeExpandingTextareas`), not implicit load order. What's **not** resolved by either C1 or C2: live verification in a real consuming app. Both were large, unverified-outside-this-repo changes landing the same day, ahead of a same-day rollout (B2: Launchpad today) — see [specs/16](specs/16-convert-js-to-esm.md)'s Outcome for the full residual-risk accounting.

## Email partials (`app/views/will_style/components/email/`)

- **Business criticality**: Moderate-to-high depending on the consuming app — transactional email is often business-critical (password resets, notifications), but this gem only supplies the styling/markup partials, not the sending logic.
- **Test coverage**: None, and notably **harder to catch regressions here than for in-app CSS** — email client rendering quirks mean a broken partial may not surface until a real client (Outlook, Gmail, etc.) renders it, well past any review step.
- **Coupling**: Depends on `premailer-rails` in the consuming app, which is **not a declared dependency** of this gem — it's documented only in the README as the consuming app's responsibility. If a consuming app omits it or uses a different inliner, these partials may not render as intended.
- **Understood?**: Reasonably — the partials are conventional (button/footer/styles/table) and self-explanatory, but the implicit `premailer-rails` dependency is a gap.

## Local image-processing pipeline (`gulp/`, `gulpfile.js`, `package.json` devDependencies)

- **Business criticality**: Low — this is a contributor-facing dev tool for generating responsive image variants; it doesn't ship in the gem's runtime output, and `src/`/`dist/` are gitignored.
- **Test coverage**: None (none expected for a local CLI tool of this kind).
- **Coupling**: Low functionally, but **fragile operationally**: depends on a private `git+ssh` fork (`gulp-sharp-responsive`) with no npm registry release, plus a `node_modules` currently out of sync with the lockfile (see [dependency-audit.md](dependency-audit.md) — the `sharp` drift is also a live CVE exposure for anyone who hasn't recently run `npm install`).
- **Understood?**: Yes — the single task file is short and well-commented; the risk here is availability/reproducibility, not comprehension.

## Ruby-side helper code (`app/helpers/will_style/library_helpers.rb`, `lib/will_style/engine.rb`)

- **Business criticality**: Low — small surface area (one helper method, one engine file).
- **Test coverage**: None.
- **Coupling**: Low — self-contained.
- **Understood?**: Mostly, with one confirmed bug: `WillStyle.stylesheets_path` (`lib/will_style/engine.rb:41-43`) calls an undefined `assets_path` method and would raise `NoMethodError` if ever invoked. A repo-wide grep found no callers — likely dead code, but worth confirming before deleting (see [open-questions.md](open-questions.md)) since it's a public method on the gem's namespace and a downstream consumer could theoretically call it.

## Cross-cutting: no test harness, no CI, no lint

This isn't a per-area risk, it's the systemic one: **every change to every area above ships without any automated check.** Given will-style is a shared dependency across multiple production apps, the current process for catching a regression is "someone notices the styling/behavior looks wrong in a consuming app after a version bump." Establishing even minimal coverage (a Ruby test harness with a dummy Rails app for the engine, a lint pass for SCSS/JS, and ideally a lightweight visual-regression check for the SCSS output) is foundational — most other modernization work becomes safer once this exists, which is why the roadmap should treat it as a first-order Foundation item rather than an optional nice-to-have.
